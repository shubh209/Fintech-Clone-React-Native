Current App Flow And Features

This is the actual user journey implied by the current route tree and docs.

Public entry
Landing, signup, login, help, and phone verification live under apps/frontend/app. Clerk handles auth and SecureStore caches tokens.
Signed-in shell
After sign-in, Expo Router sends users to /(authenticated)/(tabs)/home. The active primary tabs are Home, Activity, and Crypto.
Home
Balance and recent transaction state. It hydrates transaction snapshots from the Worker, updates optimistically, and shows sync/fallback status.
Activity
Searchable and filterable transaction history, category labels, editable custom categories, and monthly income/spending/net totals.
Crypto
Market list plus detail screens. Mobile calls the deployed Worker through EXPO_PUBLIC_API_BASE_URL; the Worker owns CoinMarketCap and fallback behavior.
Security modals
Authenticated modal routes include lock and account flows. Inactivity storage also has MMKV plus memory fallback behavior.

Current Risks And Open Loops

These are the areas where you should be careful before saying the project is production-like.

High Signed-in transaction smoke test

The Worker rejects missing or malformed bearer tokens correctly, but the docs still call out a manual signed-in Expo smoke test with a real Clerk session token as the next step.

Medium Transaction durability still snapshot-based

Home and Activity now sync to the cloud, but mutations are optimistic snapshots rather than a richer transaction event model. That is okay for this stage, but it matters for conflict handling.

Low Crypto fallback history

Fallback ticker history may still be BTC-specific when live selected-asset quotes are unavailable. Per-asset fallback seeding is a future product decision.

Medium Roadmap drift

The Phase 1 plan file mentions local Expo API handlers, but the repo has moved to a Cloudflare Worker architecture. Treat docs as living references, not orders.

Decisions You Should Own Next

This is where control shifts back to you. Pick one row, write down why, then implement the smallest measurable version.

Decision Why It Matters Good Junior Engineer Move Measurement Signal
Should Goals become the next tab? It would turn the app from tracking into planning, but only if it is a real workflow. Build one savings goal with target amount, progress, and local validation before adding broad goal types. Supported goal workflow count: 0 to 1; tests for create/update/progress states.
Should Activity get richer budgeting first? It builds on existing transaction categories and monthly totals. Add monthly category budget thresholds and visible over/under state. Budget insight states: none to under/near/over; metric for threshold warnings rendered.
Should transaction sync become more robust? It strengthens the production engineering story before adding more UI. Add conflict/error retry handling or a manual refresh flow with clear status. Retry paths covered by tests; fallback recovery scenarios increase.
Should crypto fallback data be expanded? It makes offline or provider-failure crypto details less misleading. Seed per-asset fallback data and document freshness tradeoffs. Fallback accuracy coverage: BTC-only to selected tracked assets.

Suggested working rule: when an agent recommends a step, ask it to identify the user-facing outcome, the files it expects to touch, the risk level, and the measurement signal before it writes code. That keeps you as the product and engineering decision-maker.
